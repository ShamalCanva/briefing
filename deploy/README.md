# Putting the brief on a live site

This folder is a complete, dependency-free host for the brief: a single Node server that serves the page behind a passphrase, stores briefs on disk, and accepts a new brief each morning through a secret-protected endpoint. Your calendar, Slack and Zoom content is on the page, so it is never served without the passphrase.

## Fly.io (recommended)

Fly gives you a persistent volume and a Sydney region, which is all this needs.

```bash
cd Briefing/deploy
fly launch --no-deploy --copy-config --name shamal-brief --region syd   # keeps fly.toml; pick any free name
fly volumes create brief_data --region syd --size 1
fly secrets set SITE_PASSWORD='<a long passphrase you will type to open the site>' \
                INGEST_SECRET="$(openssl rand -hex 32)"
fly deploy
fly open            # you'll land on the passphrase screen
```

Then tell the publish script where to send briefs (these two files are gitignored):

```bash
mkdir -p ../.deploy
echo "https://shamal-brief.fly.dev" > ../.deploy/site_url
fly secrets list    # INGEST_SECRET shows only a digest; paste the value you generated above:
echo "<the INGEST_SECRET value>" > ../.deploy/ingest.secret
./push-brief.sh ../briefs/2026-10-08.json   # → {"ok":true,"date":"2026-10-08"}
```

Reload the site and today's brief is there. The Refresh button re-fetches `/api/brief`, so when the morning job publishes a new one it appears without redeploying.

## Vercel

Vercel works but needs two substitutions, because serverless functions have no writable disk and production password protection is a paid add-on. Store briefs in Vercel Blob (`@vercel/blob`: `put('briefs/latest.json', body)` in the POST handler, `head`/fetch in the GET), and gate the site with a `middleware.ts` that checks the same session cookie `server.js` sets and redirects to `/login` otherwise. The route logic in `server.js` ports line for line into `api/brief.ts` and `api/login.ts`. If you'd rather not, Fly is less work.

## How the morning update works

Nothing on the server talks to Slack, Zoom or Google. The server only receives finished `Briefing` JSON. The brief is generated by Claude in the Cowork app using the connectors you've already authorised, then pushed with `push-brief.sh`. That keeps every provider credential inside Claude's connectors and leaves the site with exactly two secrets: the passphrase and the ingest secret.

The weekday 06:30 schedule is set up inside Claude (ask for it in the chat). Each run reads your sources, writes `briefs/YYYY-MM-DD.json`, verifies every link and commitment quote against what it fetched, and runs `push-brief.sh`. If a run fails, the site keeps showing the previous brief, stamped with its generation time, so you can always tell how fresh it is.

If you later want the site to generate briefs itself (so Refresh truly re-reads your accounts), that is the backend described in `../ARCHITECTURE.md` with its own OAuth apps. This host is the Phase 0 it describes.

## Security notes

The passphrase and secret are compared in constant time, login is rate-limited per IP, the session cookie is HttpOnly/Secure/SameSite, and responses are `no-store`. The ingest endpoint accepts only a document that looks like a brief, capped at 2 MB. Rotate `INGEST_SECRET` with `fly secrets set` and update `.deploy/ingest.secret`; rotating `SITE_PASSWORD` logs every browser out. To revoke access entirely, `fly apps destroy shamal-brief`.
